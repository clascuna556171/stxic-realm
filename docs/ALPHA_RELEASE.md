# Alpha release rehearsal and recovery

This is a release checklist, not approval to deploy. The linked project's state is disputed: a prior shared handoff reports that the three 29 October migrations and two functions were deployed; other project notes report them pending. Do not infer the ledger or function versions from either account. An operator must inspect the actual target, migration contents and configuration before selecting a rollout. The later `20261029030000_profile_media_cleanup_safety.sql` is an additional forward-only migration.

## Local preflight

Run `pnpm release:preflight`, `pnpm test:database`, `pnpm test`, `pnpm typecheck` and `pnpm build`. The preflight only inventories local files, hashes migrations and reports whether Git is dirty; it does not contact a server or certify safety. Review and freeze the exact source, function versions, lockfile and build outputs. Do not run `test:social:sql`: it explicitly targets the linked project. Existing integration scripts create and delete identities and require an independently verified disposable target.

## Isolated staging

1. Obtain a dedicated disposable Supabase project or isolated local stack with Docker, separate credentials, test mail and its own Storage. Confirm the project reference and endpoint in each command and in the dashboard. Never repoint or reset the linked development project for tests. Do not put service credentials into browser environment variables or logs.
2. Record the actual migration ledger and compare it with the reviewed local files and checksums. Resolve any divergence manually: a matching timestamp alone does not prove matching SQL. Back up first, then apply only missing migrations in order, including `20261029000000`, `20261029010000`, `20261029020000` and `20261029030000`. Do not reapply a migration already recorded. Check the existing `realm-profiles` bucket is private with the intended limits; `ON CONFLICT DO NOTHING` does not repair a mismatched bucket.
3. Configure exact test origins and deploy the reviewed `realm-profile-media` and `realm-worker` versions only to the disposable target. Verify JWT, function gateway configuration, service secrets, scheduler authentication and failure alerts. Do not copy production user data into disposable tests.
4. With separate admitted users and an outsider, verify allowed and denied home, hall, profile and Storage operations; decorator and membership revocation; stale revisions; old layouts; binary format, size, dimension, frame, count and byte limits. Verify raw Storage writes and unpublished/hidden/blocked reads are denied even with a generic permissive policy. Check signed URLs expire and that previously issued URLs may remain valid until expiry. Exercise upload retry, delete during upload, account deletion, worker failure/retry and queued blob removal after the one-hour grace period. Confirm pending/ready blobs are never selected for garbage collection. Include independent connections and a deliberately interrupted upload; SQL shims do not test Storage behavior.
5. Verify real reconnect and network loss, keyboard/focus, reduced motion, desktop and phone layouts, and returning to and sending a message in chat after a world-rendering failure. Test accessibility with assistive technology and perform the five-user alpha/load, mail and moderation exercises. Record commands, target identity, versions, results and failures without credentials.

## Backup and restore

Before any authorized hosted change, take and verify a provider-supported database backup covering Auth and application data, separately inventory and back up Storage objects and relevant function/configuration versions, and record the migration ledger and restoration point. Confirm backup retention, encryption, access, expected recovery point and downtime with the operator. Restore into a separate isolated project, never over the active project for a rehearsal. Confirm identities, message/history, home and hall layouts, profile metadata and corresponding objects; exercise RLS and signed URLs with test identities. Record what cannot be restored, including any Auth secrets or external settings. A database dump alone is not a Storage blob backup. Rehearse and time recovery before alpha.

## Authorized staging rollout and rollback

Freeze a reviewed release and backup, compare target ledger, bucket configuration and deployed function versions, and stop on any divergence. Deploy the required missing migrations in chronological order, then compatible functions and worker, verify their configuration and smoke-test with test identities, then publish the web build. Confirm no secret is embedded in the client bundle. Monitor errors, storage queues and scheduler. Use a named operator, stop/go criteria and an incident communication channel.

For frontend/function regressions, stop new traffic where possible and restore the previously recorded compatible web build and function versions. Schema migrations are forward-only: do not blindly reverse them, delete the bucket, reset the database or restore over live writes. Assess whether the previous frontend/functions remain compatible; otherwise prepare a reviewed forward fix. For severe data corruption, stop writes and follow the rehearsed restoration plan with explicit authorization, accounting for writes since the backup. Verify permissions, layouts, blobs and worker recovery after rollback. Never claim rollback is tested until the rehearsal succeeds.

## Windows and web release gates

`docs/ARCHITECTURE.md` proposes a Tauri shell with React/Vite; there is currently no `apps/desktop/src-tauri` implementation or installer. A Vite web build is not a Windows installer. The desktop shell, secure production origins and auth callback behavior, WebView2 prerequisites, signed installer, update strategy, clean-machine install/uninstall and Windows browser-to-desktop authentication must be implemented and tested before distribution. The proposed Cloudflare Pages target likewise needs an authorized staging environment, reviewed public variables, HTTPS origins, callback allowlist, CSP/security headers and deployment/rollback verification. Actual hosted publishing is an external gate.
